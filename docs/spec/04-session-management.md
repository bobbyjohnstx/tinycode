# 4. Session Management

Package: `internal/session/`

Sessions are the core unit of conversation. Each session contains an ordered list of messages, a reference to a model and agent, and metadata about token usage and file changes.

## 4.1 Session Info

```go
type Info struct {
    ID        string     // ses_<sortable-id>
    Slug      string     // ID without prefix, used in URLs
    ProjectID string     // directory-based project identifier
    Directory string     // working directory for this session
    ParentID  string     // parent session ID (empty for root sessions)
    Title     string     // display title
    Agent     string     // active agent name
    Model     *ModelRef  // provider/model reference
    Version   string     // schema version ("1")
    Summary   *Summary   // file change summary (additions, deletions, files, diffs)
    Cost      float64    // accumulated cost
    Tokens    TokenUsage // accumulated token usage
    Time      TimeInfo   // created/updated timestamps (milliseconds)
}
```

### Token Usage

```go
type TokenUsage struct {
    Input     int        // prompt tokens
    Output    int        // completion tokens
    Reasoning int        // reasoning/thinking tokens
    Cache     CacheUsage // cache hit/write tokens
}

type CacheUsage struct {
    Read  int
    Write int
}
```

### Session IDs

Generated by `internal/id/` with ascending time ordering and `ses_` prefix. The slug strips the prefix for URL use.

### Default Titles

| Type | Format |
|------|--------|
| Root session | `"New session - "` + RFC3339Nano timestamp |
| Child session | `"Child session - "` + RFC3339Nano timestamp |

## 4.2 Session Store vs SessionManager

| Layer | Package | Role |
|-------|---------|------|
| `session.Store` / `MessageStore` | `internal/session/` (`session.go`, `message.go` — no `store.go`) | SQLite persistence for sessions and messages |
| `SessionManager` | `internal/server/` | In-process runtime: active prompts, abort, system prompt build, revert stash, bus events |

### Operations (`session.Store`)

| Method | Description |
|--------|-------------|
| `Create(input)` | Insert new session, auto-generates ID and slug |
| `Get(id)` | Fetch session by ID |
| `List(projectID, limit, offset, includeArchived)` | List sessions for a project, newest first; archived excluded by default |
| `Children(parentID)` | List child sessions |
| `UpdateTitle(id, title)` | Update session title |
| `UpdateCost(id, cost, tokens)` | Replace cost and token counts |
| `AddUsage(id, costDelta, tokens)` | Cumulatively add token counts; `costDelta=0` leaves cost unchanged |
| `UpdateSummary(id, summary)` | Update file change summary |
| `Archive(id)` / `Unarchive(id)` | Set or clear archive timestamp |
| `Delete(id)` | Hard delete session row |

### Project Tracking

`ensureProject()` creates a project row (`INSERT OR IGNORE`) on session creation, keyed by `projectID` with the `worktree` directory.

## 4.3 Messages

```go
type Message struct {
    ID        string    // msg_<sortable-id>
    SessionID string
    Role      string    // "user", "assistant", "system"
    Model     string    // model ID that generated this message
    Parts     []Part    // content parts
    Tokens    int       // estimated token count
    CreatedAt time.Time
}
```

### Message Parts

```go
type Part struct {
    Type       PartType // text, tool_call, tool_result, reasoning
    Text       string
    ToolCallID string
    ToolName   string
    ToolArgs   string   // JSON string
    ToolResult string
    ToolError  bool
}
```

| PartType | Constant | Description |
|----------|----------|-------------|
| Text | `PartText` | Plain text content |
| Tool Call | `PartToolCall` | Tool invocation (name + JSON args) |
| Tool Result | `PartToolResult` | Tool execution output |
| Reasoning | `PartReasoning` | Reasoning/thinking content |

### Message Store

| Method | Description |
|--------|-------------|
| `Append(msg)` | Insert message (parts stored in message blob JSON) |
| `ReplaceAll(sessionID, msgs)` | Atomically replace session history (used after compaction) |
| `List(sessionID)` | List messages for a session, oldest first |
| `DeleteByID(messageID)` | Delete a message by ID |
| `DeleteAfter(sessionID, messageID)` | Delete all messages after a given message (keeps target) |
| `DeleteAfterTime(sessionID, afterMs)` | Delete messages with `time_created` after cutoff |

## 4.4 Processor

The processor (`Processor`) is the main LLM loop that processes user prompts.

### Processor Config

```go
type ProcessorConfig struct {
    SessionID        string
    Agent            string
    Model            *provider.Model
    MaxSubagents     int        // unused today; depth limits live on tool.Context
    SystemPrompt     string
    Compaction       CompactionConfig
    AgentPerms       []string
    DoomThreshold    int
    AutoContinueMax  int
    Directory        string     // session working directory (from session.Info)
    CompactionModel  string
    SmallModel       string
    Temperature      *float64
    TopP             *float64
    MaxTokens        *int
    MaxIterations    int        // 0 = use default (200)
    Perms            *permission.Service
    Ruleset          permission.Ruleset
}
```

### Constants

| Constant | Value | Description |
|----------|-------|-------------|
| `maxIterations` | 200 | Default max LLM round-trips per prompt |
| `maxConsecutiveToolFailures` | 10 | Abort after this many consecutive failures |
| `consecutiveToolFailureWarnEvery` | 3 | Emit warning every N consecutive failures |

### Processor Loop

```
User prompt → addUserMessage()
  ↓
Loop (up to maxIter()):
  1. checkAbortAndContext() — bail on abort or context cancellation
  2. runLLMStep() — stream LLM response, accumulate assistant message
  3. handleLLMError() — retry on transient errors
  4. checkCompaction() — compact if token budget exceeded
  5. Publish "session.message" to bus
  6. Extract tool calls from assistant message
  7. If no tool calls:
     - tryAutoContinue() → loop if auto-continue budget remains
     - Otherwise return ProcessResult
  8. checkDoomLoop() — detect repetitive tool call patterns
  9. runToolCalls() — execute tools, collect results, check consecutive failures
  10. Continue loop
```

### Process Result

```go
type ProcessResult struct {
    Messages  []Message    // final message list
    Usage     TokenUsage   // total token usage
    Error     error        // nil on success
    Aborted   bool         // true if user aborted
    Compacted bool         // true if history was compacted this turn
}
```

### Abort

`Processor.Abort()` sets `p.aborted = true` under mutex. The loop checks `isAborted()` at the start of each iteration.

### Max Iterations

`maxIter()` returns `ProcessorConfig.MaxIterations` if > 0, otherwise the default 200. Exceeded iterations produce an error in the `ProcessResult`.

## 4.5 Session Manager

Package: `internal/server/` (`session_manager.go`, `session_ops.go`, …)

The `SessionManager` coordinates session lifecycle within the HTTP server:

- Creates sessions with `session.Store`
- Resolves models via `provider.Registry`
- Resolves agents via `agent.Registry` (with compact variant for small models ≤8B)
- Spawns `Processor` instances for prompt execution
- Publishes bus events for session creation/deletion
- Manages shutdown: drains all active processors on `Shutdown()`

Subagents are synthetic (`parentSessionID:label`) via `RunSubagent` / the task tool — not separate `Store` rows. `MaxSubagents` on `ProcessorConfig` is unused. Manual summarize (`POST /session/{id}/summarize`) runs `Processor.Compact` and returns `200` + `{"compacted": bool}`. Session share/unshare and PTY HTTP APIs remain deferred ([16-not-implemented.md](16-not-implemented.md) §16.11–16.12).

### Session Fork

Forking creates a child session with:
- Same project, directory, agent
- Copied message history from parent (Append failures delete the fork and return an error)
- `ParentID` set to the source session
- Auto-resolves model (falls back to first available if configured model missing)

## 4.6 Auto-Continue

When the LLM produces a response with no tool calls, the processor checks whether prior turns had tool calls (`hadPriorToolCalls`). If so, and the auto-continue budget hasn't been exhausted, it injects a continuation prompt and loops again.

**Default auto-continue max:** 0 (disabled). This is intentional — it was set to 0 to prevent runaway loops with local models.

## 4.7 Doom Loop Detection

The processor tracks recent tool call signatures. If the same sequence of tool names + truncated args repeats, it indicates the model is stuck in a loop. When detected, the processor returns an error result.

`DoomThreshold` is configurable via `ExperimentalConfig.DoomLoopThreshold` in config.
