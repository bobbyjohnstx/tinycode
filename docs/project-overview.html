Data Flow

How data moves through the system

Four critical flows power tinycode. Click through each step or press Play to watch the animation.

1
User types prompt
User enters a message in the TUI prompt textarea. Pressing Enter submits.
connectedApp.submitPrompt()
2
HTTP POST to server
The API client sends the prompt to the embedded HTTP server via POST /session/:id/prompt.
api.Client.CreatePrompt()
3
Session processor starts
The session processor enters its agent loop: build messages, send to LLM, process response.
session.Processor.Process()
4
LLM streaming begins
The LLM client opens an SSE connection to the provider (Ollama, vLLM, OpenRouter) and streams text deltas.
llm.Client.ChatCompletionStream()
5
Tool calls parsed & executed
If the LLM emits tool calls, each is executed via the tool registry with permission checks.
tool.Registry.Execute()
6
Events flow to TUI via SSE
All state changes are published to the event bus and streamed to the TUI as SSE events (text deltas, tool results, status).
bus.Publish() → SSE → mapSSEToMsg()
7
TUI renders response
The bubbletea Update() function processes each SSE message, updating the model. View() re-renders the terminal output.
App.Update() → App.View()
1
Binary discovery
Plugin manager searches ~/.config/tinycode/plugins/ and PATH for plugin binaries matching the config list.
plugin.Manager.Load(name)
2
Spawn child process
The plugin binary is launched as a child process. Communication happens over stdin/stdout using JSON-RPC 2.0. Binaries are named tinycode-plugin-<name> on PATH or in the config plugins directory.
exec.Command("tinycode-plugin-<name>")
3
Initialize handshake
Host sends "initialize" request with version and directory. Plugin responds with manifest declaring its tools and hooks.
JSON-RPC "initialize" → {id, tools, hooks}
4
Tool & hook registration
Plugin-provided tools are added to the tool registry with namespaced IDs. Hooks are registered with the hook dispatcher for lifecycle events.
registry.Register("plugin__{name}__{tool}", ...)
5
Event dispatch loop
During operation, tool calls dispatch "tool/call" and lifecycle events dispatch "hook/invoke" to the plugin process.
"tool/call" | "hook/invoke" → plugin
6
Clean shutdown
On exit, the host sends a dispose hook, waits for acknowledgment, then closes stdin and kills the process.
"hook/invoke" dispose → kill
1
Registry.Execute() called
The session processor calls the tool registry with tool name, arguments, and session context.
Registry.Execute(ctx, name, args, sessionID)
2
Lookup & disabled check
The registry looks up the tool definition by name and verifies it is not in the disabled tools map.
lookup Def by name → check disabled map
3
Permission check
The permission service is consulted. If the tool requires approval, a prompt is published to the bus and blocks until the user replies.
permission.Service.Ask() → blocks for reply
4
Before hook & execute
A "tool.execute.before" bus event fires. Then the tool's Execute function runs with the provided context and arguments.
bus.Publish("before") → def.Execute()
5
Plugin after-hook
The result is dispatched to any plugins with ToolExecAfter hooks. Plugins can modify the output (e.g., truncate, sanitize).
AfterHook → plugin dispatch
6
Return result
The final output is truncated if needed, then returned to the session processor as (output, isError).
bus.Publish("after") → return (output, isError)
1
Event triggers
A lifecycle event fires: session_start, tool_exec_before, tool_exec_after, or a custom event defined in settings.json hooks.
bus.Publish("session.start") | bus.Publish("tool.execute.before")
2
Shell hook or plugin hook dispatch
The hook dispatcher checks settings.json for shell hooks and the plugin manager for registered plugin hooks. Both are invoked in parallel.
settings.hooks[event] → exec.Command() | plugin "hook/invoke"
3
additionalContext returned
Hooks can return additionalContext in their response. This text is collected from all hook responses and prepared for injection.
hookResult.AdditionalContext → collect
4
Context injected into next model call
The collected additionalContext is appended to the system prompt or injected as a system message in the next LLM request, enriching the model's context.
additionalContext → system prompt → llm.ChatCompletionRequest

JSON-RPC Wire Protocol
initialize
Host sends version + directory. Plugin returns manifest with tools and hooks.
→
tool/call
LLM invokes a plugin tool. Params use the args field (not arguments). Plugin returns a result string.
→
hook/invoke
Lifecycle event dispatched. Plugin processes and optionally returns output.
→
dispose
Clean shutdown. Plugin flushes data, closes connections, releases resources.

Technology

Technology stack

Every dependency was chosen for one reason: ship a single binary with zero runtime requirements.

Go
Go 1.27.1+
Systems language for the entire codebase. Static linking, fast startup, low memory footprint, cross-compiles to 5 platforms.
Replaced TypeScript/Bun. No runtime dependency, instant startup.
bbt
bubbletea
Terminal UI framework using Elm architecture (Model/Update/View). Deterministic state, testable without a terminal, async via tea.Cmd.
Elm architecture prevents callback spaghetti in complex TUI state.
mux
net/http ServeMux
Standard library HTTP router. Pattern-based routing, middleware via handler wrapping, no third-party router dependency.
Zero external deps for HTTP. Same code path for TUI, web UI, and ACP.
SQL
modernc.org/sqlite
Pure Go SQLite implementation. No CGO dependency. Sessions, messages, and project metadata persist across restarts.
Pure Go = no C toolchain needed for cross-compilation.
lip
lipgloss
Terminal styling and layout library. CSS-like API for padding, margins, borders, and colors in the terminal.
Consistent styling across terminal emulators and color profiles.
glm
glamour
Markdown rendering for the terminal. Renders LLM responses with syntax highlighting, code blocks, and formatted text.
Rich markdown display without leaving the terminal environment.
Get Started

Up and running in 60 seconds

Install the binary, connect a model, and start coding with AI in your terminal.

01
Install
One-liner installs to ~/.local/bin. Or build from source if you prefer.
bash
# One-liner (macOS / Linux) curl -fsSL https://raw.githubusercontent.com/bobbyjohnstx/tinycode/main/install.sh | sh # Or Homebrew brew install bobbyjohnstx/tap/tinycode # Or build from source git clone https://github.com/bobbyjohnstx/tinycode.git cd tinycode && make build ./dist/tinycode
02
Diagnose and connect
tinycode doctor reports what is missing. It does not configure a model. Auto-discovery finds Ollama, vLLM, and LM Studio. If none is found, /connect in the TUI picks one. There is no tinycode setup wizard.
bash
# Example: pull a model with Ollama ollama pull qwen3:8b # Or use OpenRouter (cloud) export OPENROUTER_API_KEY="sk-or-..." # In the TUI, if no model is discovered: /connect
03
Launch tinycode
The TUI starts instantly. Type a message and press Enter. Use Tab to switch agents, <leader>m to change models.
bash
# Launch TUI in current directory tinycode # Or target a specific project tinycode ~/projects/myapp # Browser chat, headless API, IDE, or one prompt tinycode web tinycode serve tinycode acp tinycode run "explain the main function" # Multi-turn with NDJSON output tinycode run --multi-turn --format json # Cap iterations, skip permissions tinycode run --max-iterations 20 \ --dangerously-skip-permissions "summarize"
04
Configure (optional)
Set default model, enable plugins, customize agents. Config supports JSONC (comments allowed).
jsonc
// ~/.config/tinycode/tinycode.jsonc (or tinycode.json / config.json) { "model": "ollama/qwen3:8b", "small_model": "ollama/qwen3:1.7b", "default_agent": "build", "plugins": ["safety-net"] }
